# A1 source-compiled scalar UI import (experimental)

This deliberately narrow first source-to-service proof uses the actual maintained
JS/TS parser, semantic binding identities, structured numeric IR and Wasm emitter.
It is **not** a general ES module resolver, a complete Component Model compiler,
a public DOM API or an acceptance claim for the A1 application.

The opt-in Rust compiler entry point is `compile_ui_import(source, typescript)`.
Ordinary `compile`, `compile_value` and `compile_async` continue to reject
runtime imports. Source files must explicitly import one named service:

```js
import { selectVisible as choose } from "grunkalunka:a1/ui";
export function run(a, b) {
  return choose(a, b);
}
```

The supported service is exactly `selectVisible(Number, Number) -> Number`;
the compiler recognizes the imported binding by Oxc semantic symbol identity,
not by its local spelling. Left-to-right argument evaluation, value snapshots,
ordinary discarded surplus arguments and existing numeric source quotas are
retained. The generated **core Wasm** imports
`"grunkalunka:a1/ui" / "select-visible"` with two `f64` arguments and one
`f64` result. Neither the source language nor core module has an ambient
document, filesystem or network binding. The host must explicitly link the
service.

Ordinary named numeric helpers can call the imported service or compose around
it, including forward, self and mutually recursive calls within the existing
source and guest execution limits. Source function identities remain independent
of the imported core-Wasm function index; ordinary import-free artifacts retain
their existing indexing. Existing synchronous runtime closures, captured cells,
factories and managed captures can compose with the same import. Function-value
identities retain their logical closure-table slots; the table's targets account
for the imported core function. Numeric captured-cell entry points still reset
their invocation arena, while managed captures use the existing traced cells
and function objects. No reference crosses the scalar service boundary.
The service binding remains a direct call target; reifying that imported function
as a stored value or passing it itself as a callback remains unsupported.

The profile is not exposed through the ordinary CLI/build API; the Rust compiler
API and integration tests are the
supported experimental entry points. Unsupported imports, missing/incorrect
source bindings, spread service arguments, optional service calls and
out-of-profile expressions remain
rejections, not silently substituted shims.

## Real provider and dual-engine proof

`crates/grunkalunka-runtime/tests/a1_ui_import.rs` compiles paired JS/TS
sources, inserts their **actual imported core module** into a private component
template, and instantiates that component against the **Rust-implemented**
`grunkalunka:a1/ui` WIT service in Wasmtime. No handwritten adapter calls
an import-free compiled function. A missing provider fails linking, a denied
profile fails with a distinguishable policy error and zero state transitions,
and a granted provider admits the authorized heading count only. Changing the
source operation changes the Rust provider's returned visible count and state.

An independent Node/V8 core-Wasm test checks the emitted import ABI and
source argument order with a small local test double. That double is **not**
the WIT authority proof; the Wasmtime/Rust path supplies it. The same portable
core Wasm bytes are used by both engines; no new Actions workflow is added.

The helper-composition tests compare actual source execution in native JavaScript,
the same generated bytes in Node-Wasm, and the real Rust WIT provider. They check
provider argument order, discarded surplus-argument effects, state and results,
forward/recursive targets, import-name shadowing, denial, and JS/TS byte equality.
Closure cases cover reassigned callees, shared captures, returned factories,
per-iteration numeric cells, managed object captures, callable array fields and
canonical module-function identities. Repeated calls into the same WIT instance
include copying collections between invocations. This does not add host-retained
callbacks, asynchronous imported calls, managed service payloads or a shared
application heap across independently instantiated entries.

Nested-binding composition cases use the same native JavaScript, Node-Wasm and
Rust WIT comparison. One helper extracts a nested action record and captures its
Boolean/String leaves in a handler. Another handler extracts grouped heading
records through a mixed object/array declaration, then uses a destructuring
`for...of` head with a lazy identifier default to compute the visible count.
An optional-action case supplies missing view, group and heading-option records
through whole-pattern defaults before deriving the service arguments.
These records and boxed leaves stay within compiled source; the handler passes
derived numeric arguments through the unchanged scalar service. The cases add
no numeric unboxing, typed public A1 payload or resource interface.

From the repository root, after fetching locked dependencies, run:

```sh
cargo test -p grunkalunka-runtime --test a1_ui_import --locked
```

The separate [A1 source-driven interaction](a1-service-interaction.md) tracks
application input, native Rust control and reflow/repaint integration. The source
composition tests here do not establish those application acceptance gates.
A typed UI action/view resource remains separately scoped in
[#483](https://github.com/tseguine/grunkalunka/issues/483), including its authority,
ownership, lifetime and failure contract. The scalar import does not settle that
public boundary or its marshalling cost.
